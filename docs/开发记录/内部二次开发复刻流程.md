# 内部二次开发复刻流程（跨会话工作流）

> **面向读者**：在外部仓库协作的 Claude 会话、负责公司内复刻的开发者。
> **状态**：自 `internal-dev` 分支起，对所有应用层改动生效。任意新会话在首次涉及应用层工作前**必须先读本文件** + 根 `CLAUDE.md` 的「内部二次开发复刻」章节 + dev-spec 模板。

---

## 一、背景与目标

- 本项目原在公司外开发，现搬入公司内做**二次开发**。内外网络隔离，公司内有独特开发规范/组件，依赖版本可能不同，两端代码最终会分叉。
- 当前任务聚焦**应用层 / 业务逻辑改动**，对开发依赖的需求低（多为可移植的逻辑改动）。
- **目标**：外部仓库做出可运行的参考实现 + 可复刻的开发说明；公司内按说明复刻，**最大程度保持代码统一**。

---

## 二、分支策略

- 从 `main` 拉单一长期工作分支 `internal-dev`，所有应用层改动在此分支顺序提交。
- **不在 `main` 上直接改应用层代码**。
- 每个逻辑改动 = 一份 dev-spec 文档 + 对应代码提交（可同一 commit）。
- 分支名可按公司规范重命名，但须保持「单一长期工作分支」语义。

---

## 三、交付物模型

- **真实代码 + 配套 dev-spec 文档**：外部分支是可运行的参考实现；dev-spec 是叙述 + 关键片段，指导公司内复刻。
- **代码是 ground truth，dev-spec 是导航**。公司内复刻时以 dev-spec 为指引、以分支代码 `git diff main..internal-dev` 为兜底对照。
- dev-spec 精度：**散文 + 关键代码片段**，不要求逐行 diff（需要时可附 `git diff` 片段）。

---

## 四、dev-spec 规范

- **位置**：`docs/开发记录/dev-specs/NN-短名.md`（`NN` 为两位序号，按时间递增；`短名` 用中文或英文短语概括任务）。
- **模板**：[`docs/开发记录/dev-specs/_模板.md`](dev-specs/_模板.md)。每份 dev-spec 必须覆盖模板全部章节。
- **必含**：需求背景、现状分析、方案设计、改动清单、**依赖敏感点**、验证方式、复刻步骤。
- **依赖敏感点**单列一节：标注该改动涉及的外部依赖/版本/组件，以及公司内可能的差异与适配建议。无则填「无」。

---

## 五、跨会话一致性

- 根 `CLAUDE.md` 的「内部二次开发复刻」章节是**自动加载的硬性约束**，确保任意会话都遵循本流程。
- 新会话首次涉及应用层工作前的强制动作：读本文件 + CLAUDE.md 该节 + dev-spec 模板 + 既有 `docs/开发记录/dev-specs/` 累积记录。
- 既有 dev-spec 是累积的需求记录，新改动延续其编号与风格，不重写历史 spec。

---

## 六、公司内复刻流程

1. 拉取 `internal-dev` 分支（或获取其 dev-spec 文档集），按 `NN` 序号顺序复刻。
2. 逐份读 dev-spec：理解需求/设计 -> 按改动清单定位文件 -> 应用改动（用关键片段对照，必要时 `git diff` 兜底）。
3. 命中**依赖敏感点**时，按其标注的公司内适配说明替换（依赖版本/组件差异）。
4. 按 dev-spec「验证方式」验证（单测 / 手动检查），对照预期结果。
5. 复刻完一份，提交公司内仓库，commit 信息与外部一致以便对照。

---

## 七、依赖差异处理

- 每个 dev-spec 单列「依赖敏感点」：外部依赖、版本、公司内可能差异、适配建议。
- 若某依赖在公司内无对应，dev-spec 须给出替代方案或回退路径。
- 跨多个 dev-spec 的公共依赖映射，按需维护 `docs/开发记录/dev-specs/依赖映射.md`。

---

## 八、提交规范

- 每个 dev-spec 对应一次（或一组）提交。
- commit 信息格式：`feat/app-layer(NN): 简述` 或 `docs/spec(NN): 简述`，正文引用 dev-spec 路径与依赖敏感点摘要。
- **仅按用户明确要求 push**；默认本地提交。

---
