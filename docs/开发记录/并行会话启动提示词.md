# 并行会话启动提示词

> 本文件是并行会话的**自举入口**。新会话只需被粘贴下面一句即可开始：

```
读 CLAUDE.md（已自动加载）+ docs/开发记录/并行会话启动提示词.md，开始任务 NN：<任务简述>
```

---

## 一、文档地图

`docs/` 三区划分，每份文档一句话：

```
docs/
├── README.md                              ← 总索引（本目录唯一入口）
├── 开发记录/
│   ├── 内部二次开发复刻流程.md             ← 跨会话工作流总纲（必读）
│   ├── 并行会话启动提示词.md               ← 本文件
│   ├── dev-specs/
│   │   └── _模板.md                        ← dev-spec 模板（新任务复制它）
│   └── 开发方案/
│       ├── MCP工具权限隔离-开发方案.md      ← mcp-server 工具权限+文件 ACL（切面+装饰器）
│       ├── 文件权限-应用端开发方案.md       ← utils 文件 ACL（纯装饰器，无切面）
│       └── phase2-日志审计开发方案.md       ← Phase2 审计日志（行为+管理员操作）
├── 技术方案/
│   └── spring-ai-harness-安全体系技术方案(正式版).md  ← 评审用安全体系（五层纵深+管理台+文件ACL）
└── 图集/                                   ← 8 张 drawio（对应技术方案第七节图索引）
```

- **开发记录**：工作流 + 逐任务记录 + 专题方案。`dev-specs/` 按 `NN` 序号累积，新任务延续编号、不重写历史 spec。
- **技术方案**：评审用，关心**为什么做、做什么**，不关心函数签名/代码行号。
- **图集**：drawio 图，修改后必须做坐标几何校验 + XML 转义校验（XML 合法 ≠ 布局正确）。
- 模块级文档（mcp-server）在 `spring-ai-harness-mcp-server/docs/`，自包含、不动。

## 二、dev-spec 模板必含章节

每份 dev-spec（`docs/开发记录/dev-specs/NN-短名.md`）必须覆盖 [`_模板.md`](dev-specs/_模板.md) 全部章节：

1. **元信息**：编号 NN、标题、状态、关联分支
2. **需求背景**：为什么做
3. **现状分析**：当前代码/架构事实（基于探查，非假设）
4. **方案设计**：怎么做（散文 + 关键代码片段，不要求逐行 diff）
5. **改动清单**：新增/改动文件
6. **依赖敏感点**：外部依赖/版本/组件，公司内可能差异与适配建议（无则填「无」）
7. **验证方式**：单测/手动检查 + 预期结果
8. **复刻步骤**：公司内按说明复刻的顺序

精度原则：**代码是 ground truth，dev-spec 是导航**。散文 + 关键片段，需要时附 `git diff` 片段兜底。

## 三、工作流硬规则（浓缩）

| 维度 | 规则 |
|---|---|
| **分支** | 在 `internal-dev`（从 `main` 拉出的单一长期工作分支）上改；**不在 `main` 直接改应用层代码** |
| **交付物** | 真实代码改动 + 配套 dev-spec（可同一 commit） |
| **dev-spec 精度** | 散文 + 关键代码片段；单列「依赖敏感点」 |
| **编号** | dev-spec 按 `NN` 两位序号递增，延续既有编号不重写 |
| **commit** | `feat/app-layer(NN): 简述` 或 `docs/spec(NN): 简述`，正文引用 dev-spec 路径；末尾加 `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>` |
| **push** | **仅按用户明确要求 push**；默认本地提交 |
| **远端** | `origin` = ichaobuster（上游，只读）；`fork` = toBeYoungD（可推）。`internal-dev` 跟踪 `fork/internal-dev` |
| **代理** | 全局 `http.proxy`/`https.proxy` = `http://127.0.0.1:7877`（VPN）。一次性覆盖：`git -c http.proxy=http://127.0.0.1:7877 -c https.proxy=http://127.0.0.1:7877 push ...` |
| **首次动作** | 新会话首次涉及应用层工作前：读本文件 + [`内部二次开发复刻流程.md`](内部二次开发复刻流程.md) + 根 CLAUDE.md「内部二次开发复刻」节 + [`dev-specs/_模板.md`](dev-specs/_模板.md) + 既有 `dev-specs/` 累积记录 |

复刻由开发者在公司内按 dev-spec 手动执行；本节保证跨会话一致。

## 四、并行会话协作

多个会话并行做不同任务时：

- **各自独立 worktree + 独立 task 分支**：避免互相污染工作区。每个会话从 `internal-dev` 拉自己的 task 分支（如 `internal-dev-task-NN`），完成后合回 `internal-dev`。
- **不共用同一分支**：并行会话不要在同一个分支上并发提交，否则必然冲突。
- **dev-spec 编号不撞车**：开始前先看 `dev-specs/` 已有最大 `NN`，领取下一个号；若多个会话同时启动，口头/任务表约定分配。
- **改不同文件优先**：任务拆分尽量按模块/文件边界，减少合并冲突（如一者改 mcp-server、一者改 utils）。
- **push 前先 pull**：`fork/internal-dev` 可能有别的会话刚推上去的提交，push 前 `git pull --rebase fork internal-dev`。

## 五、开始任务 NN 的检查清单

1. 读本文件 + [`内部二次开发复刻流程.md`](内部二次开发复刻流程.md) + 根 CLAUDE.md「内部二次开发复刻」节
2. 确认在 `internal-dev` 分支（或从其拉出的 task 分支）：`git branch --show-current`
3. 浏览既有 [`dev-specs/`](dev-specs/) 累积记录，领取下一个 `NN`
4. 复制 [`dev-specs/_模板.md`](dev-specs/_模板.md) → `NN-短名.md`
5. 探查现状 → 写方案 → 改代码 → 填 dev-spec 全部章节（含依赖敏感点）
6. 按「验证方式」验证（单测 `./mvnw test -pl <module>` 或手动检查）
7. 提交：`feat/app-layer(NN): 简述`，正文引用 dev-spec 路径 + 依赖敏感点摘要 + `Co-Authored-By` trailer
8. **仅当用户明确要求时** push 到 `fork`
