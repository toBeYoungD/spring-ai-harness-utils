# Spring AI Harness MCP Server 安全体系技术方案

> **面向读者**：对项目不了解的技术人员。阅读本文档不需要提前阅读源码。

---

## 一、背景与问题

### 1.1 AI 智能体的文件操作困境

现代 AI 智能体（如 QwenPaw、OpenClaw 等）需要访问文件系统来完成编程任务——读取代码、修改文件、搜索符号、执行 Shell 命令等。这些智能体由不同团队用不同语言开发，各自的文件操作实现各不相同，面临三个共性问题：

1. **路径穿越风险**：智能体可能被诱导访问 `../../etc/passwd` 这类越权路径
2. **多租户数据泄露**：同一台机器上运行的不同用户会话需要严格隔离
3. **误操作无法回滚**：智能体的破坏性写入（误删、覆盖）缺乏撤销手段

### 1.2 统一安全层的必要性

解决上述问题如果走"各自修补"的路线，每种智能体都要独立实现权限校验、隔离机制、审计回滚——投入大且质量参差不齐。核心判断是：

> **所有主流智能体都支持 MCP（Model Context Protocol）协议。禁用其内建文件工具，统一路由到一个安全的 MCP Server，即可实现"一次建设，全部受益"。**

### 1.3 本文档的范围

本文档聚焦于 mcp-server 模块的安全架构设计，从**文件管理**和**沙箱执行**两条主线展开（合并承载于"安全插件"），阐述每一层防线解决什么问题、采用什么方法论、以及各层之间的协作关系。文中不涉及具体函数签名或代码行号，重在抽象设计思路。

## 二、总体架构

### 2.1 系统分层

系统从逻辑上分为三层：

| 层次 | 职责 | 核心组件 |
|------|------|----------|
| 接入层 | 协议端点、身份提取 | MCP Streamable HTTP 端点、REST API 端点 |
| 工具层 | 文件操作、技能管理、工具中继 | FileSystemTools、SkillTools、RelayTools |
| 存储层 | 物理存储、内容处理、配额管控 | StorageProvider、FileContentProcessor、QuotaManager |

### 2.2 请求流

一个请求进入系统后的处理路径如下（以文件读取为例）：

```
MCP 客户端请求（携带 Authorization 头）
  → 身份提取：从 Header 解析三段式身份
  → 存储装配：工厂根据身份创建隔离的存储实例
  → 路径安全校验：绝对路径拒绝、前缀强制绑定
  → 工具执行：文件操作委托给存储层
  → 内容处理：InputStream 流式解析，避免 OOM
  → 返回结果
```

### 2.4 三个微应用与两大安全领域

整个安全体系由**三个微应用**承载，覆盖两大**独立安全领域**：

| 微应用 | 包含组件 | 所属领域 | 职责 |
|--------|---------|---------|------|
| **MCP tool** | 文件 MCP Server(含沙箱中继) | 领域一 | 智能体文件操作的安全执行 + 沙箱动态执行 |
| **MCP gateway** | MCP 网关 + AI 接口 MCP Server | 领域二 | 全公司 AI 接口集中化 + 网关二维权限鉴权 |
| **MCP mgr** | 统一管理台 | 跨领域 | 统一管理 MCP tool 与 MCP gateway 的策略、配置、审计 |

**领域一:智能体文件与执行安全**(MCP tool 承载)。围绕智能体的编程任务展开,内部包含两个运行时组件:

| 组件 | 角色 | 参与运行时热路径 | 面向使用者 |
|------|------|-----------------|-----------|
| **文件 MCP Server** | 智能体文件操作的安全执行者——接管所有文件读写、搜索、编辑，在身份认证、路径隔离、快照回滚、配额管控五层防线约束下执行 | 是，每次文件工具调用 | 智能体 |
| **沙箱执行环境** | 智能体动态操作的安全执行者——按需创建容器，提供 Shell/浏览器/Computer 执行能力，通过工作区挂载与文件 MCP Server 共享同一份数据视图 | 是，每次中继工具调用 | 智能体 |

这两个组件的关系:文件 MCP Server 和沙箱负责"跑",在每次智能体请求的热路径上执行安全防线。第三章（安全插件）展开文件管理与沙箱执行两大安全领域，第四章从智能体视角展开端到端协同。

**领域二:AI 接口集中化的网关鉴权**(MCP gateway 承载)。面向全公司 AI 接口统一纳管,内部包含两个组件:

| 组件 | 角色 |
|------|------|
| **MCP 网关** | 位于调用方与 AI 接口 MCP Server 之间的请求拦截层，按角色判定工具的查询权限与调用权限 |
| **AI 接口 MCP Server** | 集成全公司各系统的 AI 接口(LLM、图像、语音等)，统一封装为 MCP 工具，集中化暴露;网关放行后的请求在此转发到下游真实 AI 接口 |

领域二的身份体系独立于领域一的三段式 `{system}-{agent}-{user}`,采用公司统一的 Token 鉴权,按角色划分权限。第六章展开接口权限控制（MCP 网关）的设计。

**跨领域统一管理**(MCP mgr 承载)。MCP mgr 是统一管理台,同时管理 MCP tool(文件浏览、工具权限、配额、日志审计)和 MCP gateway(AI 接口工具的查询/调用权限策略);文件路径级 ACL 不归管理台,由用户自服务配置(见 5.3)。它不参与任何运行时热路径,只通过策略下发通道离线生效。第五章展开管理台。

> 三个微应用的关系:MCP tool 和 MCP gateway 各自承载一个安全领域的运行时,身份体系隔离、互不接入;MCP mgr 在两者之上做统一管控。两者仅因均采用 MCP 协议而并在同一文档中呈现。

### 2.5 核心设计原则（设计思路）

整个安全体系的设计哲学可以用三个原则概括，它们贯穿后续所有章节，构成整体设计的方法论基础：

| 原则 | 含义 | 体现 |
|------|------|------|
| **纵深防御** | 不依赖单一防线，多层互补 | 五层文件安全：认证→隔离→路径→快照→配额 |
| **类型安全替代运行时校验** | 通过架构设计让越权操作"不可表达" | 工厂返回的存储实例已绑定工作区前缀，工具层不可能越界 |
| **零开销可插拔** | 增强能力不应为"未启用状态"支付开销 | 装饰器模式装配，关闭时直接返回原始实现，无运行时条件分支 |

而文件管理（静态安全）与沙箱执行（动态安全）的分离，本质上是对**资源利用率的优化**——将高频无状态的操作和低频有状态的操作分开处理，各取所需的隔离等级，避免过度保护造成的资源浪费。这一思想直接催生了第三章"安全插件"的打包方式：将两类安全能力统一暴露给智能体，但对内按资源特征分别治理。

## 三、安全插件

> **安全插件**是承载"智能体文件与执行安全"这一安全领域（领域一，由 MCP tool 微应用承载）的核心组件集合。它将文件管理与沙箱执行两类能力打包为一组智能体可统一调用的"安全工具"，在身份认证、工作区隔离、路径安全、快照回滚、配额管控等防线约束下执行。

### 3.1 文件管理安全体系：五层纵深防线

文件管理安全并非单点机制，而是一组纵深排列的防线。每一层防范的威胁不同，各层互为补充；缺了任何一层，整体安全性就会出现缺口。

#### 3.1.1 第一层：身份认证

**防御目标**：未授权请求、身份伪造。

**设计思路**：

采用**三段式身份模型**：`{system}-{agent}-{user}`，通过 HTTP `Authorization` 请求头传递。系统级标识来源，智能体级区分同一系统内的不同实例，用户级区分最终使用者，三者组合形成粒度的隔离单元。

身份提取遵循**抽象接口 + 可插拔实现**的模式。默认使用 Header 解析，支持连字符和斜杠两种分隔格式，并自动剥离 `Bearer` 前缀。扩展时可切换为 JWT 校验等任意自定义认证逻辑，无需改动工具层。

**设计要点**：

- 身份信息**无状态传递**：服务端不存储会话，每个请求自包含身份凭证，天然支持水平扩展
- 认证失败的请求在入口处被拒绝，不会接触到存储层，实现"fail-early"

#### 3.1.2 第二层：工作区隔离

**防御目标**：跨用户、跨智能体的数据泄露。

**设计思路**：

身份信息在存储层被映射为**物理路径前缀**。不同身份的前缀天然不同，物理上不可能交叉访问。路径映射遵循 `{ossPrefix}/{system}-{agent}-{user}/` 规则，例如 `mcp/workspaces/openclaw-code-assistant-alice/`。

这一映射发生在**工厂装配环节**——工具层仅需获取"属于当前请求的存储实例"，而完全不感知映射逻辑。由此工具层与身份/隔离逻辑彻底解耦，且隔离边界由架构强制保证：每个请求拿到的存储实例已绑定工作区前缀，不可能越界。

**设计要点**：

- 从智能体的视角看，工作目录永远是 `./`，它感知不到 OSS 上的完整物理路径
- 智能体看到的"根目录"与 OSS 上的绝对路径之间构成不可逾越的鸿沟——这正是隔离的核心

#### 3.1.3 第三层：路径安全

**防御目标**：路径穿越攻击（如 `../../`）、绝对路径越权访问。

**设计思路**：

将所有路径操作收敛到**唯一的路径拼接点**，在此处集中执行校验规则：拒绝绝对路径、强制前缀绑定、归一化 `./` 前缀。收敛到单点是路径安全设计中的关键——分散处理路径必然存在遗漏，单点则意味着**安全逻辑只需在一处编写、审计和维护**。

**补充说明**：

- OSS 对象存储的 Key 是字面字符串，`..` 在 OSS 中不具有 POSIX 语义的目录跳转功能。但为适应未来可能将工作区挂载到 POSIX 沙箱，路径中仍需对 `..` 做净化处理
- 系统内部路径（`.snapshots/`、`.trash/`、`.shadow/`）在目录列表中自动过滤，智能体无法感知

#### 3.1.4 第四层：操作审计与回滚

**防御目标**：智能体误操作、恶意指令导致的文件破坏。

**设计思路**：

采用**自动前置快照**策略——在 Write（覆盖已有文件）、Edit、Trash 三类破坏性操作执行前，系统自动保存当前状态。此机制对智能体强制生效，不可选择。快照数据存储于工作区内部的 `.snapshots/` 目录，对智能体不可见（被路径过滤规则拦截）；每个快照含文件内容的完整副本及元数据（文件路径、操作类型、时间戳）。

回滚操作设计了**双重兜底**：系统在执行 Rewind 前，自动创建一份"回滚前"快照（标记为 `REWIND`）。这保证了任何回滚都有一条"后悔"路径——如果回滚方向错误，可再次回滚恢复到回滚前状态。

**设计要点**：

- 快照机制对智能体透明——智能体调用工具时并不知道快照已被创建
- 快照创建失败不阻塞主操作——这是非侵入式的安全增强，不是核心路径的依赖

#### 3.1.5 第五层：资源配额管控

**防御目标**：单个智能体工作区无限制膨胀，耗尽存储资源。

**设计思路**：

采用**装饰器模式**将配额校验与业务逻辑分离。配额管理器以工作区为单位追踪存储用量，通过元数据文件持久化已用量并支持增量更新；在存储工厂的装配环节，将基础存储实例包装进配额装饰器，装饰器在写操作前检查配额、写操作后增量更新。快照、回收站、影子缓存是否计入配额可独立配置。

配额关闭时工厂直接返回原始实例，不经装饰器，无性能损耗。这种"构造阶段结构差异"实现了零开销可插拔——不是运行时 `if` 分支，而是不同配置走不同的对象装配路径。

### 3.2 沙箱执行安全体系

文件管理仅覆盖"静态安全"——数据在存储层的保护与隔离。当智能体需要执行 Shell 命令、操作浏览器时，涉及"动态安全"——运行时行为的容器化隔离。这就是沙箱执行体系要解决的问题。

#### 3.2.1 核心设计决策：文件系统与沙箱分离

将文件操作与 Shell/浏览器置于同一沙箱中看似直观，但两类操作在资源特征上差异显著：

- **文件操作**是高频、无状态、多租户可共享的。一次对话可能产生数十次文件读写。这些操作不需要容器隔离——只要路径前缀隔离就能保证安全
- **Shell/浏览器操作**是低频、有状态、必须隔离的。执行 `npm install` 或打开网页需要完整的操作系统环境，而且每个智能体会话必须拥有独立的进程空间

若将两者合并，每个智能体需独占一个容器，文件操作与运行时耦合于同一进程空间内。这意味着即使仅读取一个文件，也需等待容器就绪；且容器数量与用户数线性增长——每个用户一个容器，一百个用户即一百个容器，资源开销不可低估。

**分离后的收益**：

- 文件 MCP Server 可以**无状态水平扩展**，用少量实例服务大量用户
- 沙箱容器**按需创建**，只在智能体真正需要执行 Shell 或浏览器操作时才启动
- 两者独立扩容、独立计费

#### 3.2.2 沙箱生命周期管理

**设计思路**：采用**懒加载（Lazy Load）模式**。

沙箱并非预分配。智能体启动时，MCP Server 仅注册沙箱工具的**工具描述（Tool Definition）**，不建立到沙箱的实际连接。工具描述包含了工具名、参数 schema、功能说明，足以让框架层的工具调用管理器识别这些工具的存在。

只有当智能体**实际调用**了一个沙箱工具（如 `run_shell_command`）时，沙箱客户端才被真正创建和初始化：创建到沙箱 MCP 端点的连接、建立 MCP 会话并完成协议初始化、将工具调用转发到沙箱执行。会话结束后关闭连接，沙箱容器可被回收。

**设计要点**：

- 若智能体在整个对话中从未调用沙箱工具，容器永远不被创建——资源零消耗
- 工具描述预加载的成本极低（仅内存中的 schema 对象），无需网络连接
- 沙箱客户端使用完毕后必须关闭，以防堆外内存泄漏

#### 3.2.3 工作区挂载

沙箱内的 Shell 执行需要访问智能体的文件数据——不具备文件访问能力则 `ls`、`cat` 等命令失去操作对象。

**设计思路**：

沙箱容器在创建时，将该智能体的 OSS 工作区路径**挂载**到沙箱内的 `/workspace` 目录。这个挂载的路径前缀就是 MCP tool 中 `{system}-{agent}-{user}` 前缀的目录。

关键安全含义：

> 沙箱里看到的文件范围 = MCP Server 为该智能体隔离的工作区范围 = `{system}-{agent}-{user}` 前缀下的所有文件

这意味着智能体 A 在沙箱里看到的文件与其通过 MCP 文件工具操作的文件是**同一套数据**；沙箱内即使执行破坏性操作，也仅影响容器内的挂载视图，不会波及其他用户数据；沙箱销毁后容器内状态随之清除。

#### 3.2.4 工具中继代理

智能体需要调用沙箱内的 Shell、浏览器等工具，但这些工具并非本地可执行——它们依赖沙箱容器内的完整运行时环境。为此，MCP Server 内置了**工具中继（Relay）机制**。它在设计定位上是一个 MCP 协议透明代理：自身注册为 MCP Server，但对于特定工具（Shell、Browser、Computer 等约 40 个工具）透明转发请求到下游的沙箱 MCP Server。

智能体感知不到中继的存在——调用 `run_shell_command("ls /workspace")` 时，请求在 MCP Server 内部经过中继识别、身份透传、转发、执行、结果回传，对智能体而言只是"调了一个工具"。

**关键设计决策**：

- 中继连接携带与原始请求相同的 Authorization 头，保证沙箱侧也能识别身份，完成工作区挂载
- 中继功能是可配置开关（`relay.enabled`）。关闭时这些工具直接从 MCP Server 的工具列表中消失
- 中继工具与本地文件工具在同一个 MCP 端点下共存，对客户端完全透明

#### 3.2.5 安全闭环总结

文件管理（静态安全）和沙箱执行（动态安全）的关系：

```
              ┌─────────────────────────┐
              │      MCP Server          │
              │                          │
  ┌───────────┤  文件工具（安全文件操作）  │
  │           │  中继工具（透明转发沙箱）  │
  │           └───────────┬──────────────┘
  │                       │
  │ 同一套身份体系          │ 同一套身份体系
  │ 相同的隔离前缀          │ 相同的工作区挂载
  │                       │
  ▼                       ▼
┌──────────┐      ┌──────────────┐
│ OSS 存储  │      │  沙箱容器      │
│ 工作区 A  │◄────►│ /workspace   │
│ 工作区 B  │      │ (按需创建)    │
│ 工作区 C  │      └──────────────┘
└──────────┘
```

两者的安全边界由同一套身份体系定义。沙箱内看到的数据集和 MCP 文件工具操作的数据集是一致的——都是该 `{system}-{agent}-{user}` 前缀下的文件。这保证了**无论智能体通过哪种路径操作文件，都受到相同的隔离约束**。

## 四、智能体如何使用这套安全体系（端到端视角）

前面第三章（安全插件）从"文件管理"和"沙箱执行"两条主线讲了安全体系的设计。这一章换一个视角——按"**动机 → 方案 → 效果**"的逻辑，阐述智能体在一次完整任务中，这套体系如何全程介入。

### 4.1 动机：安全对智能体必须透明

智能体的本职是完成编程与操作任务，而不是理解安全策略。如果安全要求智能体"主动配合"——比如自行校验路径合法性、自行判断自身权限——会带来两个问题：

- **复杂度转移给不可靠的一方**：安全校验逻辑一旦下沉到智能体，既增加其上下文负担，又因智能体本身的不可控性留下安全缺口（被诱导绕过只是时间问题）。
- **越权操作仍可"被表达"**：只要智能体手里能拿到别的身份的存储实例或别的容器的入口，错误地调用就是可能的。

因此设计目标是：**智能体始终只面对"一组统一的工具"，安全体系在它感知不到的地方全程介入；身份（Authorization 头）是贯穿所有防线的唯一线索。** 这正是将文件管理与沙箱执行打包为同一"安全插件"、并让智能体只看到一组工具的初衷——它将"安全"从智能体的职责中剥离，交给架构强制执行（呼应 2.5 的"类型安全替代运行时校验"原则：越权操作在架构层面就"不可表达"）。

### 4.2 方案：一个工具面、一条身份线索、两个世界

为实现"智能体只看到一组工具、安全全程无感介入"，领域一的两种能力收敛到同一个 MCP 端点下，并由身份这条唯一线索将它们绑定：

- **统一工具面**：智能体禁用自身的内置文件工具（原生 fs、child_process 等），转而连接 Harness MCP Server，拉取文件工具、技能工具、中继工具（沙箱相关）的定义并注册到自己的工具集。对智能体而言，它只知道"我有一组工具"，并不区分这些工具背后是本地文件操作还是远程沙箱。
- **一条身份线索贯穿所有防线**：智能体的每一次请求都携带 `Authorization: {system}-{agent}-{user}` 头。这个身份是整个安全体系的起点——MCP Server 从头里提取身份，后续的隔离前缀、配额、沙箱挂载全部由它派生。身份无状态传递，服务端不存会话，天然支持水平扩展。
- **两个世界，同一边界**：文件工具用它派生 OSS 前缀（静态安全的"文件世界"），中继工具将它透传给沙箱用于 `/workspace` 挂载（动态安全的"执行世界"）。两个世界用同一套身份体系划定边界，但智能体始终以为自己在一台机器上自由操作。
- **越权在架构层面不可表达**：智能体拿不到别的身份的存储实例，也不存在别的容器的入口。只要它在自己的工作区内活动，就不会遇到任何"权限不足"的拦截——因为越权操作从根上就构造不出来。

### 4.3 效果：智能体使用安全的五个生命周期阶段

将上面的机制落到智能体的真实使用上，完整生命周期可分为五个阶段：

**阶段一：启动与工具注册。** 智能体禁用自身的内置文件工具，转而连接 Harness MCP Server，拉取文件工具、技能工具的定义并注册到自己的工具集。如果启用了沙箱，沙箱工具的定义也会被预注册--但此时**不创建任何沙箱容器**，只是将工具的 schema 登记进来。对智能体而言，它只知道"我有一组工具"，并不区分这些工具背后是本地文件操作还是远程沙箱。

**阶段二：会话发起（身份贯穿）。** 智能体的每一次请求都携带 `Authorization: {system}-{agent}-{user}` 头。这个身份是整个安全体系的起点：MCP Server 从头里提取身份，后续的隔离前缀、配额、沙箱挂载全部由它派生。身份无状态传递，服务端不存会话，天然支持水平扩展。

**阶段三：文件操作（静态安全介入）。** 智能体调用 Read/Write/Edit 等工具时，请求带着身份头到达 MCP Server。Server 为该身份装配出一个专属的隔离存储实例（前缀已绑定），随后路径校验、前置快照、配额检查等防线逐层介入。智能体感知到的只是"我读写了一个相对路径下的文件"，它不知道自己被关在一个前缀隔离的工作区里，也不知道每次改文件前系统替它存了快照。

**阶段四：执行操作（动态安全介入）。** 当智能体需要跑 shell 或操作浏览器时，它调用中继工具（run_shell_command 等）。首次调用触发沙箱懒加载--容器启动、工作区挂载到 `/workspace`；后续调用复用连接。沙箱执行结果透明返回。智能体感知到的只是"我执行了一条命令并拿到了输出"，它不知道命令实际跑在一个按需创建、用完回收的容器里，更不知道那个容器的文件视图和自己用文件工具操作的是同一份数据。

**阶段五：会话结束与资源回收。** 会话结束时，沙箱连接关闭、容器回收；而工作区数据持久留在 OSS 上，下次同一身份再来，还能访问到之前的文件、快照、回收站。静态安全的数据是持久的，动态安全的容器是临时的--这正是两者分离的价值。

**一条线索，两个世界。** 将五个阶段压缩成一句话：

> 智能体带着同一个身份，在"文件世界"和"执行世界"之间穿梭；两个世界用同一套身份体系划定边界，智能体却始终以为自己在一台机器上自由操作。

身份是唯一贯穿文件管理和沙箱执行的线索。文件工具用它派生 OSS 前缀，中继工具将它透传给沙箱用于挂载--无论智能体走哪条路径，它脚下的地面都被这个身份框定在 `{system}-{agent}-{user}` 之内。安全体系对智能体完全透明：它不会遇到任何"权限不足"的拦截（只要它在自己的工作区内），因为越权操作在架构层面就"不可表达"--它根本拿不到别的身份的存储实例。

参见：[智能体使用安全体系端到端流程图](#智能体使用安全体系端到端流程)

## 五、管理台（MCP mgr）：统一配置与管控层

第三章（安全插件）讲了运行时安全的两条主线--文件管理和沙箱执行(均由 MCP tool 微应用承载)。这两条线解决了智能体操作文件与执行命令时的安全执行问题。余下的问题是：**安全的策略由谁制定、如何下发、变更后如何生效**。

这就是 MCP mgr 的角色。它是三个微应用中的统一管理台,不参与任何运行时热路径,作为"配置与管控层"--管理员通过它设定权限策略、资源配额、运维规则,策略下发到 MCP tool(文件 MCP Server 和沙箱)与 MCP gateway(网关),在调用方的下一次请求中生效。

MCP mgr 的管辖范围跨两个安全领域:

| 管辖对象 | 所属微应用 | 管控内容 |
|---------|-----------|---------|
| 文件 MCP Server + 沙箱 | MCP tool | 文件浏览、工具权限、配额、日志审计 |
| MCP 网关 + AI 接口 MCP Server | MCP gateway | AI 接口工具的查询/调用权限策略（含基于角色的接口权限分配） |

### 5.1 定位：管理台作为独立微应用的必要性

权限配置、配额管理等策略如果直接写入 MCP tool 或 MCP gateway 的本地配置文件，变更时须重启或重部署全部实例；配置散落在各微应用中也无法形成统一的审计视图。将管理台独立为 MCP mgr 微应用，可解决以下三个核心问题：

- **配置与执行解耦。** MCP Server 为无状态服务，天然适合水平扩展。若将权限策略、配额规则都固化在它的配置文件里，每次变更均需重启或重部署全部实例。管理台独立后，策略存储于独立的存储介质中，MCP Server 通过策略接口实时拉取或接收推送，变更即时生效，不影响运行时服务。
- **面向管理员，而非开发者。** 文件管理和沙箱的工具是给智能体调用的（机器对机器）；管理台的使用方是人——运维人员、安全管理员，以及为接口权限做角色分配的业务人员。他们需要的是可视化界面、操作日志、审批流程，而不是编辑 YAML 配置文件。这是两种截然不同的交互模型。
- **审计与决策可追溯。** 谁在什么时候改了谁的权限、谁批准了配额提升--这些操作记录是合规的基础。独立管理台天然带审计日志，不与执行日志耦合。

### 5.2 管理台功能板块（管理员侧）

管理台的四个功能板块面向管理员（`X-Admin-Token` 鉴权）：文件存储管理、工具权限、配额、日志审计。文件路径级的读写权限不在此列--它交给用户自服务配置（见 5.3）。

#### 5.2.1 文件存储管理（云盘式工作区管控）

管理台提供对智能体工作区文件的**离线管理**能力--管理员不需要模拟智能体请求，可以直接浏览、搜索、操作任意工作区下的文件。核心功能：

- **可视化文件浏览**：Windows 资源管理器风格的树形目录、列表/网格双视图、拖拽移动/重命名。管理员按 `{system}-{agent}-{user}` 维度选择要查看的工作区。
- **文件读写与上传**：直接在浏览器里创建、编辑文本文件；上传二进制附件（按 UUID 路径隔离存储，与智能体的工作区文件目录分离）。
- **回收站管理**：浏览 `.trash/` 目录中被智能体删除的文件，支持恢复或彻底清除。
- **快照浏览与回滚**：查看任意文件的历史快照列表（按操作类型过滤），一键 Rewind 恢复到指定版本。这是在智能体已经离线的情况下，管理员手工执行的补救操作。
- **跨工作区文件操作**：管理员持有管理员令牌（`X-Admin-Token`），可以跨越工作区隔离边界，在不同 `{system}-{agent}-{user}` 的工作区之间移动或复制文件。这个能力对智能体完全不可见--智能体的请求永远被限定在自己的工作区前缀内。

#### 5.2.2 工具权限管控

这是管理台区别于通用云盘的核心能力--**对智能体可调用哪些 MCP 工具做精细化管控**。权限策略从粗到细分为三级：

**第一级：智能体级权限。** 控制一个 `{system}-{agent}-{user}` 身份能否使用某类工具。例如，禁止某一租户下的所有智能体调用 shell 工具，或只允许特定智能体使用浏览器工具。这是最粗的颗粒度，对应"这个智能体有没有资格碰这一类操作"。

**第二级：工具级权限。** 控制某类工具中的具体子项是否启用。中继工具当前涵盖 26 个工具（23 个 `browser_*`、`computer`、`run_shell_command`、`run_ipython_cell`），加文件工具 10 个、技能工具 2 个，管理员为每个身份勾选或禁用其中任意一个，形成该身份的工具白名单。

**第三级：参数级权限。** 控制工具调用时的参数约束。例如，`run_shell_command` 可以执行的命令白名单/黑名单、最长执行超时、是否允许网络访问；`browser_navigate` 可以访问的域名白名单；`browser_file_upload` 允许上传的文件大小上限。参数级权限在工具调用被转发前做准入校验，拦截不符合规则的请求。

**关键设计决策：tools/call 拦截，不裁剪工具列表。** 权限判定只作用在 `tools/call`（工具实际调用）环节，不裁剪 `tools/list`（工具列表查询）--智能体仍能看到全部工具，但越权调用在调用环节被拦截，返回权限不足。这样策略变更即时生效于下一次调用，不存在"列表里看到了就能调"的陈旧授权；判定逻辑与工具列表解耦。

**关键设计决策：权限白名单 + 中继工具开关联动。** 中继工具本身已有 `relay.enabled` 总开关。权限系统的开关在此基础上叠加：即使中继总开关开启，单个智能体的 shell 权限被关闭后，`run_shell_command` 对该智能体在调用环节被拒。这种双层开关保证了"底层能力可部署，上层权限可管控"。

> 工具权限管的是"能不能用某类工具"（如能否用 Write 工具）；文件路径级的读写限制（能对哪些路径读写）不在此处，由用户自服务配置，见 5.3。

#### 5.2.3 配额空间管理

文件管理章节讲了配额管控的运行时机制（装饰器模式、逐操作计数）。管理台这一侧提供的是**配额的运营界面**：

- **用量查看**：按 `{system}-{agent}-{user}` 组合维度展示每个工作区的已用容量 / 配额上限 / 使用率，图表化的用量趋势；支持按 `system` 或 `agent` 聚合查看。
- **配额设置**：按 `{system}-{agent}-{user}` 组合设定配额上限，每个组合一份独立上限，调整后即时生效于下一次写操作校验。未显式设上限的组合回退全局默认（1 GB）。
- **计入项配置**：是否将 `.snapshots/`、`.trash/`、`.shadow/` 纳入配额可独立配置。
- **重算**：元数据文件过期或损坏时自动触发全量重算；管理员也可手动触发。
- **告警**：用量接近配额上限时触发告警（通知管理员或直接返回配额不足错误给智能体）。

配额的计量维度是 `{system}-{agent}-{user}` 组合（即工作区）：一个组合对应一个 OSS 前缀、一份配额。这与工作区隔离（防线二）的隔离单元一致--隔离到哪，配额就管到哪。

#### 5.2.4 日志审计

- **智能体行为日志**：记录智能体的每一次工具调用--身份、工具名、入参、出参、耗时、成功失败、时间戳。覆盖文件工具、技能工具、中继工具（中继工具不经存储层，靠工具调用切面覆盖）。供事后排查和合规审计。
- **管理员操作日志**：记录管理员的所有管理操作--谁在什么时候改了谁的权限、调整了谁的配额、跨工作区操作了哪个文件。这是合规的基础，与执行日志分离。

行为日志的记录与工具权限判定（5.2.2）复用同一个 `@McpTool` 调用切面--一次拦截同时做权限判定与审计记录，不重复埋点。审计日志按时间分区存储，支持留存周期。

### 5.3 文件权限：用户自服务

工具权限（5.2.2）管的是"能不能用某类工具"，由管理员配置；而"能对哪些路径读写"这一层，**不交管理员严控，而是交给用户自己配置**--用户作为工作区的 owner，最清楚自己工作区内哪些路径需要保护。

**设计思路**：用户用自己所属的 `{system}-{agent}-{user}` 三段式身份，配置**本工作区**的路径级 ACL，约束在该工作区内运行的智能体的文件工具操作。例如把 `config/secrets.yml` 设为不可访问、把 `docs/policy/**` 设为只读，防止智能体误改敏感文件。

**与工具权限的互补关系**：工具权限（管理员配）决定"能不能用 Write 工具"，文件 ACL（用户配）决定"能写哪些路径"，两者都通过才放行。工具权限是粗粒度的总开关，文件 ACL 是细粒度的路径覆盖层；只对需要保护的特定路径加规则，业务路径走默认，避免配置爆炸。

**ACL 规则模型**：每条规则 = 路径 pattern（支持 glob，如 `docs/policy/**`、`config/*.yml`）+ 权限（可读 / 可写 / 不可访问）+ 优先级。判定时 deny 优先、最具体规则优先，无匹配规则走工具级默认。系统内部路径（`.snapshots/`、`.trash/`、`.shadow/`）仍由路径过滤规则隐藏，不进 ACL。

**关键设计决策：配置走 REST 接口，不暴露为 MCP 工具。** 文件 ACL 的配置接口是 REST 端点（用户以 `{system}-{agent}-{user}` 身份调用），不注册为 MCP 工具--智能体的工具面里没有"改 ACL"这个工具，从源头避免智能体自行改 ACL 逃逸。智能体的 `Authorization` 头由 MCP 客户端运行时持有，不进入智能体的可见上下文，进一步降低经中继 shell 工具绕过配置接口的风险。

**运行时落地**：`FileAclEnforcedStorageProvider` 装饰器（仿 `QuotaEnforcedStorageProvider`），对文件工具的每一次读写按 ACL 判定。零开销可插拔--`permission.enabled` 关闭时返回原始存储实例。

### 5.4 三层架构：管理台如何与运行时对接

管理台体系纵向分为三层，且**管理员配置与用户自服务配置共用同一套策略存储与热下发通道**，只在"谁能配什么"上分权：

```
配置面                        运行时
┌───────────────────────────┐
│ 管理员（X-Admin-Token）    │  文件存储管理 / 工具权限 / 配额 / 日志审计
│ 用户（system-agent-user）  │  文件 ACL（自服务）
└────────────┬──────────────┘
             │ 配置下发（修改即生效，不重启）
             ▼
      策略引擎（权限判定 / 配额核算 / 配置下发）
             │ 策略生效（本地缓存）
             ▼
   运行时执行层（接收管控，不感知配置面）
   请求 -> 工作区隔离 -> [切面]工具权限判定+审计 -> [装饰器]文件ACL -> 配额 -> 存储
```

- **配置面**：React 18 + Ant Design 5 的 Web 控制台。管理员侧以 `X-Admin-Token` 鉴权，管文件存储管理、工具权限、配额、日志审计；用户侧以 `{system}-{agent}-{user}` 三段式身份鉴权，管本工作区的文件 ACL。两类配置都写入策略存储。
- **策略引擎**：权限判定、配额核算、配置下发的核心逻辑。它不运行在 MCP Server 的热路径上--MCP Server 在启动或收到配置变更通知时从策略引擎拉取最新策略，缓存在本地。智能体的每次请求只查本地缓存，不做远程策略调用，保证运行时性能不受配置面影响。
- **运行时执行层**：MCP Server 的文件工具 + 中继工具 + 沙箱容器。它们对配置面无感，只接收策略引擎下发的配置（工具权限、配额上限、文件 ACL），在工具调用时执行准入校验。运行时叠放顺序为：工作区隔离（防线二）-> 工具权限判定 + 审计记录（`@McpTool` 切面，一次拦截）-> 文件 ACL 装饰器 -> 配额装饰器 -> 存储。

参见：[管理台功能体系图](#管理台功能体系)

## 六、接口权限控制

第三至五章讨论了智能体文件与执行安全（领域一，由 MCP tool 微应用承载）以及统一管控（由 MCP mgr 承载）。本章展开安全体系的第二个领域——**AI 接口集中化的接口权限控制**（由 MCP gateway 微应用承载）。该领域与领域一身份隔离、互不相关，是面向全公司 AI 接口统一纳管的独立安全设计。

### 6.1 背景与定位

公司内各业务系统对 AI 能力的依赖日益加深——LLM 对话、图像生成、语音转写、向量检索等需求持续增长。这些 AI 接口分散于不同供应商与内部服务之中，由各业务系统各自对接、各自鉴权的模式存在三重缺陷：

- **权限失控**：各 AI 接口的调用权限散落在各业务系统的代码之中，缺乏统一视图，无法审计
- **接入重复**：各业务系统均需自行处理 Token 管理、限流与错误重试，形成重复建设
- **变更被动**：AI 接口升级或下线时，需逐一通知各业务系统配合改造

针对上述问题，由 MCP gateway 微应用统一承载两件事:一是 **AI 接口 MCP Server**,将全公司用到的 AI 接口统一封装为 MCP 工具，集中化暴露;二是 **MCP 网关**,位于调用方与 AI 接口 MCP Server 之间，所有调用方(业务系统、智能体)的请求必须先过网关，由网关按公司身份体系做权限判定，放行后才转发到 AI 接口 MCP Server，再由其调用下游真实 AI 接口。

```
调用方（业务系统 / 智能体）
   │  带 Token
   ▼
MCP 网关 ── 查询权限 + 调用权限二维判定
   │  放行
   ▼
AI 接口 MCP Server ── AI 接口集中化
   │
   ▼
下游真实 AI 接口（OpenAI / Anthropic / 内部模型 / ...）
```

**与领域一的关系**。MCP gateway 和 MCP tool 是**两个完全独立的微应用**:身份体系隔离(MCP gateway 用公司统一 Token，MCP tool 用三段式 `{system}-{agent}-{user}`)、互不接入(MCP tool 不经此网关，MCP gateway 不复用 MCP tool 的防线)。两者之上由 MCP mgr 统一管控。两者仅因均采用 MCP 协议而并在同一文档中呈现。

### 6.2 基于角色的接口权限模型

接口权限控制的核心思路是：**各系统暴露的 AI 接口权限，由其调用方所拥有的角色决定**。本方案采用 RBAC（Role-Based Access Control）模型，以“角色”作为用户与接口权限之间的中间抽象层。

```
       拥有               拥有
用户 ───────► 角色 ───────► 接口权限
(业务人员分配)      (业务人员配置)
```

该模型依三条关键规则运作：

- **角色是用户与接口权限之间的桥梁**。用户不直接绑定接口权限，而是通过"拥有角色"间接获得权限。这样新增/调整接口、调整人员时，只需动角色一侧，不必逐人改权限。
- **各系统自管其角色与接口映射**。每个系统（如"客服系统""研发助手"）自行定义其 AI 接口所关联的角色，并明确"该角色拥有哪些接口的权限"。例如"图像生成角色"拥有图像生成类接口的调用权限，"语音转写角色"拥有语音类接口的调用权限。
- **角色分配由业务人员统一管理**。两件事都由业务人员（而非开发者）在管理台中维护：一是**角色拥有哪些接口权限**（定义角色的权限范围），二是**角色分配给哪些用户**（将角色指派给具体用户）。业务人员按实际业务需要分配角色，实现"谁能调什么接口"的可视化、可审计管控，权限策略不再散落在各业务系统的代码里。

这一模型与 2.5 的"类型安全替代运行时校验""零开销可插拔"原则一致：权限判定统一收口到网关一处，业务人员改角色即生效，无需改代码、无需重启服务。

### 6.3 运行时鉴权：网关的角色判定机制

角色模型定义的是"权限的来源与管理方式"，其落地执行依靠网关在请求路径上的实时判定。

**身份体系**。领域二采用公司统一的 Token 鉴权。网关从请求携带的 Token 中提取身份信息，据此查询该用户拥有的角色集合，进而判定其接口权限。具体 Token 格式与解析机制属于公司现有身份基础设施，本方案不重新设计，只消费其产出的身份信息。

**二维权限模型**。网关对 MCP 工具的权限控制划分为**两个正交维度**，分别作用于请求生命周期的不同环节：

| 维度 | 作用环节 | 含义 | 不通过的表现 |
|------|---------|------|-------------|
| **查询权限** | `tools/list`(工具列表查询) | 该身份**能看到**哪些工具 | 工具从列表中消失，调用方根本不知道它存在 |
| **调用权限** | `tools/call`(工具实际调用) | 该身份能**实际使用**哪些工具 | 调用时被拦截，返回权限不足 |

**拆分为两维的必要性。** 这是本设计的核心抽象：

- **查询权限管"可见性"**。一个 AI 接口(比如"高成本图像生成")如果对某个业务系统不可见,该系统的工具列表里根本不会出现它--调用方连"有这个工具"都不知道,从源头消除了误调用和试探调用。这比"看得见但调不了"更安全,也降低了调用方的认知负担(只看到自己能用的)。
- **调用权限管"可执行性"**。即便一个工具对某身份可见(出现在列表里),实际调用时仍要再判一次。这一层防御应对两种情况:一是权限在列表查询之后被收回(策略变更),调用时再次校验;二是某些工具需要"可见但受限调用"--比如让用户知道有这个能力,但实际调用要走单独审批。两层独立判定,纵深防御。

两个维度都基于同一套身份体系及其角色集合做判定,但判定逻辑独立--查询权限通过不等于调用权限通过。

**请求处理流程**。一次完整的工具调用经过网关的两道关卡:

```
① 调用方发起 tools/list（查询可用工具）
   -> 网关提取身份(system/org/user)，查出角色集合
   -> 查询权限判定：按角色过滤出该身份可见的工具子集
   -> 返回裁剪后的工具列表

② 调用方对某个可见工具发起 tools/call（实际调用）
   -> 网关再次提取身份，查出角色集合
   -> 调用权限判定：该角色集合能否使用此工具
      ├─ 命中拒绝 -> 直接返回权限不足，不转发到 AI 接口 MCP Server
      └─ 命中允许 -> 放行，转发到 AI 接口 MCP Server
   -> AI 接口 MCP Server 调用下游真实 AI 接口
   -> 结果原路返回
```

**关键设计决策**:

- **拒绝在网关终止**。权限不足的请求在网关就被拒绝,不会到达 AI 接口 MCP Server,更不会消耗下游 AI 接口的配额。这将"无权调用"的成本降到最低--一次网关判定,不产生任何下游开销。
- **二维判定各自独立**。查询权限的通过不缓存为调用权限的通行证,`tools/call` 时必定重新判定。这保证权限策略变更能即时生效于下一次调用,不存在"列表里看到了就能调"的陈旧授权。
- **网关对调用方透明**。调用方感知到的是"一组 MCP 工具",不知道前面有网关。它照常发 `tools/list` 和 `tools/call`,网关在背后做裁剪和拦截。这与领域一"安全对智能体透明"的理念一致。

### 6.4 小结

MCP 网关用"**角色驱动的接口权限 + 查询权限/调用权限二维判定**"，在 AI 接口集中化的唯一入口上做请求拦截。它将分散在各业务系统的 AI 接口权限收口到一个统一判定点：用户能调什么接口，取决于其拥有的角色，而角色与接口的映射、角色与用户的分配都由业务人员在管理台中维护。配合 AI 接口 MCP Server 的接口集中化能力，实现"一次建设，全公司 AI 调用统一鉴权、业务人员可管"。
