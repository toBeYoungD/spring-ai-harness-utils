# 文件权限（应用端）开发方案 - spring-ai-harness-utils

> **面向读者**：熟悉本仓库 `spring-ai-harness-utils` 模块的开发人员。阅读前建议先了解 [安全体系技术方案](spring-ai-harness-安全体系技术方案(正式版).md) 第 5.3 节（文件权限：用户自服务）与 [MCP 工具权限隔离-开发方案](MCP工具权限隔离-开发方案.md)（mcp-server 侧方案，本文是其对照）。
>
> **状态**：方案待评审。范围边界见 1.3，三个待确认事项见文末「待确认事项」。

## 一、背景与目标

### 1.1 需求

在 `spring-ai-harness-utils` 模块（应用端 SDK）中，为 `StorageProvider` 增加**路径级文件 ACL**：应用在装配工作区存储时，可声明工作区内哪些路径**可读 / 可写 / 不可访问**，约束经 `StorageProviderTools` 暴露给智能体的文件工具操作。例如 `secrets/**` 不可访问、`src/**` 可写、`docs/**` 只读。

本方案只做**应用端的 enforcement（执行）**：ACL 规则由应用在构造存储时注入，装饰器在运行时拦截。**不含管理端**（无 REST 自服务配置界面、无管理台 UI）--那属于 MCP mgr 微应用，见技术方案 5.3，本期不涉及。

### 1.2 与既有安全体系的关系

`spring-ai-harness-utils` 是 SDK，`StorageProvider` 是工作区存储抽象（`LocalFileStorage` / `AliyunOssStorage`）。工作区隔离由应用在构造 `StorageProvider` 时绑定根目录 / OSS 前缀完成（等价于 mcp-server 的 `{system}-{agent}-{user}` 前缀隔离，但在 SDK 层面是一次性绑定，非每请求解析）。

本方案新增的文件 ACL 处理的是**同一工作区内的运行时路径管控**--在已隔离的工作区内，进一步约束部分路径的读写。这是对「类型安全替代运行时校验」哲学的**补充**：隔离层保证跨工作区不可越界（拿不到别的工作区存储实例），ACL 层在同一工作区内做细粒度路径管控。

整个特性由 `enabled` 开关控制，**默认关闭**。关闭时不包装装饰器，应用拿到原始 `StorageProvider`，**零开销**（符合「零开销可插拔」原则，与 `QuotaEnforcedStorageProvider` 同构）。

### 1.3 范围边界

| 维度 | 本方案 | 不做（原因） |
|---|---|---|
| 模块 | `spring-ai-harness-utils` | 不动 mcp-server 那份 `StorageProvider`（split-package，两份独立，mcp-server 侧见参考方案） |
| 权限维度 | 仅文件 ACL（路径级读写） | 不做工具权限（工具级开关属 mcp-server 切面方案） |
| 侧 | 仅应用端 enforcement | 不做管理端 REST 自服务配置（属 MCP mgr，本期不涉及） |
| 身份模型 | 无 per-request 身份 | utils 是 SDK，`StorageProvider` 实例即工作区，ACL 随实例绑定 |
| 拦截机制 | `StorageProvider` 装饰器 | 无切面、无 ThreadLocal、无 AOP 依赖 |

> **与 5.3 的衔接**：技术方案 5.3 描述的「用户自服务配 ACL」是**配置面**（管理端 REST），本方案是**运行时执行面**（装饰器）。未来管理端落地后，其产出的 ACL 规则可经策略存储 + 热下发通道写入本装饰器消费的 `FileAclConfig`，二者接口对齐即可衔接，本期不实现该通道。

## 二、现状分析

基于对 `spring-ai-harness-utils` 模块的探查，关键事实如下：

| 维度 | 现状 |
|---|---|
| 身份模型 | **无 per-request 身份概念**。`StorageProvider` 实例由应用构造时绑定根目录 / OSS 前缀，一个实例 = 一个工作区。无 `WorkspaceIdentity`、无 `Authorization` 头解析。 |
| 工具注册 | `StorageProviderTools` 用 Spring AI `@Tool`（非 `@McpTool`），持有**单个** `StorageProvider` 字段，构造器注入。无注解扫描器、无切面包裹。 |
| 拦截机制 | **无任何切面 / 拦截器 / Filter** 包裹工具或存储调用。 |
| 存储装配 | **无工厂、无 autoconfig**。应用自行 `new LocalFileStorage(baseDir)` 或 `AliyunOssStorage`，再 `StorageProviderTools.builder(storage).build()`。装饰器链由应用手动套叠。 |
| `StorageProvider` 接口（utils 那份） | `subDirProvider` / `exists` / `isDirectory` / `listDirectory` / `readString` / `readImage` / `readAllLines` / `writeString` / `delete` / `rename` / `glob` / `grep` / `getInfo` / `getInfo(List)`(default) / `createDirectory`。**无** `trash` / `writeFile` / `readPdf` / `readDocument` / `calculateTotalSize` / `createDownloadLink`（这些是 mcp-server 那份的扩展）。 |
| 内部路径 | utils 接口仅 `IGNORED_PATH_PATTERN`（`.git/` / `node_modules/` / `target/` 等，用于列表过滤）。**无** `.snapshots/` / `.trash/` / `.shadow/`（快照/回收站机制在 mcp-server，utils 无）。 |
| 异常出口 | utils **无** `GlobalRestExceptionHandler`。`StorageProviderTools` 各工具方法内部 `catch IOException` 返回 `"Error: ..."` 字符串；`write` / `glob` 额外 `catch Exception`。错误以字符串回传智能体，不抛出。 |
| `Edit` 实现 | `StorageProviderTools.edit` = `readString` + `writeString`（无独立存储方法），与 mcp-server 一致。 |
| AOP 依赖 | pom **未声明** `spring-boot-starter-aop`，亦无 actuator 带入。 |
| 模块边界 | utils 与 mcp-server **各自一份** `StorageProvider`（split-package，同名同包 `io.github.springai.harness.storage.StorageProvider`）。本方案只动 utils 那份。 |

**关键结论**：

- **文件 ACL 的天然落点**是 `StorageProvider` 装饰器（仿 mcp-server 的 `QuotaEnforcedStorageProvider`，但针对 utils 接口）。装饰器对 `StorageProviderTools` **完全透明**--`StorageProviderTools` 无需感知 ACL，只需在构造时传入被装饰的存储。
- **无需切面、无需 ThreadLocal、无需身份解析**：utils 不区分调用方身份（单一工作区实例），ACL 随存储实例绑定，所有经该存储的调用统一判定。这比 mcp-server 方案（切面 + ThreadLocal bypass + RoleResolver）**大幅简化**。
- **`Edit` 天然覆盖**：`Edit` = `readString` + `writeString`，装饰器分别判 read / write，故 `Edit` 需该路径胜出规则为 `WRITE`。
- **异常处理需对齐既有模式**：装饰器拒绝时抛 `FileAclException`，`StorageProviderTools` 需 catch 并返回 `"Error: permission denied: ..."` 字符串（与现有 `IOException -> "Error: ..."` 模式一致），否则异常会越过工具方法直达 Spring AI 框架，错误信息不友好。

## 三、总体设计

### 3.1 结构

```
应用装配（一次性）：
  baseStorage(LocalFileStorage / AliyunOssStorage)   ← 工作区根 / OSS 前缀已绑定（隔离）
        │
        ▼
  FileAclEnforcedStorageProvider(baseStorage, FileAclConfig)   ← 本方案新增装饰器
        │  每次存储调用前按 ACL 判定路径 read/write，拒绝抛 FileAclException
        ▼
  StorageProviderTools(decoratedStorage)   ← 透明，不感知 ACL
        │  @Tool Read/Write/Edit/Glob/Grep
        ▼
  智能体 agent loop（Spring AI ChatClient）
```

`FileAclConfig` 由应用注入（程序化构造，或可选 yml `@ConfigurationProperties` 绑定）。装饰器内部持一个无状态判定器 `FileAclMatcher`，按规则集对每次调用的路径做 read/write 判定。

### 3.2 拦截位置

- **唯一拦截点**：`FileAclEnforcedStorageProvider` 装饰器，在**每个** `StorageProvider` 方法 delegate 前判定。
- **判定依据**：路径（工作区相对）+ 操作类型（read/write）+ `FileAclConfig` 规则集。
- **拒绝语义**：抛 `FileAclException`（RuntimeException），由 `StorageProviderTools` catch 转为友好错误串。
- **无 bypass 概念**：utils 中非文件工具（`SkillsTool` / `DateTimeTools` 等）不经 `StorageProvider`，天然不受影响，无需白名单旁路（区别于 mcp-server 方案的 `bypass-file-acl-tools`）。

### 3.3 与 mcp-server 方案的差异

| 维度 | mcp-server 方案（参考） | 本方案（utils） |
|---|---|---|
| 权限维度 | 工具权限（切面）+ 文件 ACL（装饰器） | 仅文件 ACL（装饰器） |
| 身份 | per-request `{system-agent-user}`，`RoleResolver` 解析角色 | 无 per-request 身份，ACL 随存储实例绑定 |
| 规则模型 | 按角色分组，allow/deny 列表 + deny-wins | 无角色，规则 = pattern + access + priority，最具体优先 + 同级 deny-wins |
| 拦截机制 | `@McpTool` 切面 + ThreadLocal bypass + 装饰器 | 仅装饰器 |
| AOP 依赖 | 需新增 `spring-boot-starter-aop` | **无需**（无切面） |
| 内部路径豁免 | `.snapshots/` / `.trash/` / `.shadow/` 放行 | **无**（utils 无这些机制路径） |
| 配置来源 | yml（`spring.ai.harness.mcp.server.permission.*`）+ autoconfig | 程序化注入为主，yml 可选（utils 无 autoconfig，应用自行 `@EnableConfigurationProperties`） |
| 异常出口 | `GlobalRestExceptionHandler -> 403` | `StorageProviderTools` catch -> 错误串 |

## 四、配置模型

采用**规则模型**（与技术方案 5.3「路径 pattern + 权限 + 优先级」一致）：每条规则 = glob pattern + 访问级 + 优先级。

```java
// 规则访问级：可读 / 可写 / 不可访问
enum Access { READ, WRITE, DENY }

// 一条 ACL 规则。priority 越大越优先（表达「最具体匹配」）。
record AclRule(String pattern, Access access, int priority) {}

// 一个工作区的 ACL 配置。
record FileAclConfig(boolean enabled, Policy defaultPolicy, List<AclRule> rules) {
    enum Policy { ALLOW_ALL, DENY_ALL }   // 无匹配规则时的兜底
}
```

### 4.1 yml 形态（可选，经 `FileAclProperties` 绑定）

```yaml
spring:
  ai:
    harness:
      file-acl:
        enabled: false                       # 总开关，默认关闭（零开销可插拔）
        default-policy: allow-all            # 无匹配规则的兜底：allow-all(向后兼容) / deny-all
        rules:
          - pattern: "secrets/**"
            access: DENY
            priority: 10
          - pattern: "**/*.env"
            access: DENY
            priority: 100
          - pattern: "secrets/public/**"     # 更具体 + 更高优先级 -> 覆盖上面的 secrets/** DENY
            access: READ
            priority: 20
          - pattern: "src/**"
            access: WRITE
            priority: 10
          - pattern: "docs/**"
            access: READ
            priority: 10
```

### 4.2 程序化形态（主推，SDK 习惯）

```java
FileAclConfig config = FileAclConfig.builder()
    .enabled(true)
    .defaultPolicy(ALLOW_ALL)
    .rule("secrets/**", DENY, 10)
    .rule("**/*.env", DENY, 100)
    .rule("secrets/public/**", READ, 20)
    .rule("src/**", WRITE, 10)
    .build();

StorageProvider base = LocalFileStorage.builder().baseDir(workspaceRoot).build();
StorageProvider guarded = new FileAclEnforcedStorageProvider(base, config);
StorageProviderTools tools = StorageProviderTools.builder(guarded).build();
```

### 4.3 规则语义

- **匹配对象**：工作区相对路径（如 `src/main/Foo.java`），与 `StorageProvider` 各方法的 `path` 入参一致。
- **glob 匹配**：Spring `AntPathMatcher`（`*` 单段、`**` 跨段）。单独 `*` = 全部路径。
- **判定算法**（路径 `P`，操作 `M ∈ {READ, WRITE}`）：
  1. 取所有 `pattern` 匹配 `P` 的规则；若无匹配 -> `default-policy`。
  2. 取匹配规则中 `priority` 最大者；同 `priority` 中 `DENY > WRITE > READ`（deny-wins）。
  3. 设胜出规则访问级为 `A`：
     - `A = DENY` -> 拒绝（不可访问）。
     - `A = WRITE` -> `READ` / `WRITE` 操作均放行（可写隐含可读）。
     - `A = READ` -> `READ` 操作放行；`WRITE` 操作拒绝（只读）。
- **最具体优先**：通过 `priority` 显式表达（用户为更具体的规则设更高优先级，如 `secrets/public/**` 优先于 `secrets/**`）。这解决了扁平 allow/deny 列表无法表达「更具体 allow 覆盖更宽 deny」的问题。
- **无内部路径豁免**：utils 无 `.snapshots/` / `.trash/` / `.shadow/`，`IGNORED_PATH_PATTERN`（`.git/` 等）是列表过滤用、与 ACL 正交，不做特殊豁免。若需禁止访问 `.git/`，显式加规则即可。
- **`default-policy=allow-all`**：向后兼容（未配置 ACL 的路径行为不变）；`deny-all`：白名单式（未显式 allow 即禁）。

## 五、新增 / 改动类清单

### 5.1 新增类（均位于 `io.github.springai.harness.storage`）

#### `FileAclConfig.java`（配置模型）

`record` + builder，字段：`enabled`、`defaultPolicy`、`rules: List<AclRule>`。内嵌 `AclRule(String pattern, Access access, int priority)` 与 `Access` / `Policy` 枚举。不可变。

#### `FileAclMatcher.java`（判定引擎，无状态）

```java
public class FileAclMatcher {
    private final AntPathMatcher matcher = new AntPathMatcher();
    private final List<AclRule> rules;
    private final FileAclConfig.Policy defaultPolicy;

    public boolean canRead(String workspaceRelativePath);   // 按 4.3 算法
    public boolean canWrite(String workspaceRelativePath);
}
```

无状态、线程安全（`AntPathMatcher` 本身线程安全）。可按 `FileAclConfig` 缓存单例。路径规范化在内部完成（去前导 `./` / `/`，去多余斜杠），与 `QuotaEnforcedStorageProvider.isExcludedPath` 的规范化逻辑对齐。

#### `FileAclEnforcedStorageProvider.java`（装饰器，仿 `QuotaEnforcedStorageProvider`）

```java
public class FileAclEnforcedStorageProvider implements StorageProvider {
    private final StorageProvider delegate;
    private final FileAclMatcher matcher;
    private final String pathPrefix;   // 根装饰器为 ""；子装饰器为 subDir（用于 subDirProvider 路径还原）

    // 每个受控方法：先 normalize -> 拼 pathPrefix -> 判定 -> 拒绝抛 FileAclException / 放行 delegate
}
```

- 构造：`new FileAclEnforcedStorageProvider(delegate, FileAclConfig)`，内部建 `FileAclMatcher`，`pathPrefix=""`。
- `subDirProvider(subDir)`：返回 `new FileAclEnforcedStorageProvider(delegate.subDirProvider(subDir), matcher, pathPrefix + subDir)`，保证子存储的相对路径能还原到工作区根相对路径再匹配 ACL。
- 受控方法见「六、拦截矩阵」。
- 默认方法（`isIgnoredPath` / `buildGlobMatcher` / `compileRegexPattern` / `fileContainsPattern` / `countMatchesInFile` / `findMatchesWithContext`）：继承接口默认实现，不覆盖（不触存储）。`getInfo(List)` 默认实现逐个调 `getInfo`，会逐个判 ACL，不覆盖。

#### `FileAclException.java`

```java
public class FileAclException extends RuntimeException {
    public FileAclException(String path, String op) { ... }   // op = "read" | "write"
}
```

RuntimeException，不进入 `IOException` 分支。

#### `FileAclProperties.java`（可选，yml 绑定）

`@ConfigurationProperties("spring.ai.harness.file-acl")`，字段与 `FileAclConfig` 一一对应，提供 `toConfig()` 转换。utils 无 autoconfig，应用需自行 `@EnableConfigurationProperties(FileAclProperties.class)`。

### 5.2 改动类

| 文件 | 改动 | 说明 |
|---|---|---|
| `tool/StorageProviderTools.java` | 五个工具方法（`read` / `write` / `edit` / `glob` / `grep`）增加 `catch (FileAclException e)`，返回 `"Error: permission denied: " + path` | 对齐既有 `"Error: ..."` 字符串模式；`write` / `glob` 现已 `catch Exception`，改为显式 catch 给统一友好信息。否则 `read` / `edit` / `grep` 只 catch `IOException`，`FileAclException` 会越过工具方法直达框架。 |
| 应用侧 `@Configuration`（非本仓库） | 装配 `FileAclEnforcedStorageProvider` 套在 base 存储外 | 示例见 4.2。本仓库不提供 autoconfig。 |

> **`StorageProviderTools` 是唯一需要改动的既有类**，且改动是纯增量 catch 子句，不破坏既有行为（`FileAclException` 仅在装饰器启用时抛出）。

### 5.3 装饰器装配顺序

```
base(LocalFileStorage / AliyunOssStorage) -> [file-acl if enabled]
```

utils 当前无 quota / observed 装饰器（那些在 mcp-server）。若应用自行套叠多装饰器，**file-acl 应放最外层**（拒绝先于其它副作用）。`enabled=false` 时不包装，应用拿到原始存储，零开销。

## 六、文件 ACL 拦截矩阵

| `StorageProvider` 方法 | 判定 | 说明 |
|---|---|---|
| `exists(path)` | read | 拒绝抛 `FileAclException` |
| `isDirectory(path)` | read | 同上 |
| `getInfo(path)` | read | 同上 |
| `getInfo(List<String>)` | read（逐个） | 继承默认实现，经 `getInfo` 逐个判定，不覆盖 |
| `listDirectory(path)` | read（基路径） | 判 `path` 可读；**不做逐条结果过滤**（见风险） |
| `readString` / `readAllLines` / `readImage` | read | 拒绝抛 `FileAclException` |
| `writeString` / `createDirectory` | write | 同上 |
| `delete(path)` | write | 同上 |
| `rename(oldPath, newPath)` | write(both) | `oldPath` 与 `newPath` 都要可写，任一不可写即拒 |
| `glob(pattern, path)` | read（基路径） | 判 `path` 可读；**不做逐条结果过滤** |
| `grep(pattern, path, ...)` | read（基路径） | 判 `path` 可读；**不做逐条结果过滤** |
| `subDirProvider(subDir)` | 跳过（重包装） | 返回带 `pathPrefix` 的子装饰器，不判定 |
| `getSeparator` / `isIgnoredPath` / `buildGlobMatcher` / `compileRegexPattern` / `fileContainsPattern` / `countMatchesInFile` / `findMatchesWithContext` | 跳过 | 默认方法，不触存储或仅纯计算 |

**`Edit` 天然覆盖**：`StorageProviderTools.edit` = `readString` + `writeString`。装饰器分别判 read 和 write：
- 胜出规则 `READ`：`readString` 放行、`writeString` 拒绝 -> `Edit` 在写阶段失败（只读路径不可编辑，符合预期）。
- 胜出规则 `WRITE`：两阶段均放行 -> `Edit` 成功。
- 胜出规则 `DENY`：`readString` 即拒绝。

## 七、关键决策汇总

| # | 决策 | 说明 |
|---|---|---|
| 1 | 仅装饰器、无切面 | utils 无 per-request 身份、无 `@McpTool`，ACL 随存储实例绑定，装饰器足够；无需 AOP 依赖 |
| 2 | 规则模型 = pattern + access + priority | 与技术方案 5.3 一致；支持「更具体 allow 覆盖更宽 deny」，优于扁平 allow/deny 列表 |
| 3 | 判定 = 最具体（高 priority）优先 + 同级 deny-wins | `DENY > WRITE > READ`；`WRITE` 隐含 `READ` |
| 4 | 无 bypass 白名单 | 非文件工具不经存储，天然不受影响（区别于 mcp-server） |
| 5 | 无内部路径豁免 | utils 无 `.snapshots/` / `.trash/` / `.shadow/`；`IGNORED_PATH_PATTERN` 与 ACL 正交 |
| 6 | 拒绝抛 `FileAclException`，`StorageProviderTools` catch 转友好串 | 对齐既有 `"Error: ..."` 模式，避免异常越过工具方法直达框架 |
| 7 | `subDirProvider` 持 `pathPrefix` 还原根相对路径 | 保证子存储视图下 ACL 仍按工作区根相对路径匹配 |
| 8 | `default-policy=allow-all` | 向后兼容，可改 `deny-all` |
| 9 | 只动 utils 那份 `StorageProvider` | split-package，不惠及 mcp-server（其自有方案） |
| 10 | 装饰器放装饰链最外层 | 拒绝先于其它装饰器副作用 |

## 八、实现步骤

| 步骤 | 内容 | 产出 |
|---|---|---|
| 1 | `FileAclConfig` + `AclRule` + `Access` / `Policy`（record + builder） | 配置模型 + 测试 |
| 2 | `FileAclMatcher`（`AntPathMatcher`、路径规范化、最具体优先 + deny-wins、default-policy） | 判定引擎 + 测试（核心，80%+ 覆盖） |
| 3 | `FileAclException` | 异常类 |
| 4 | `FileAclEnforcedStorageProvider`（装饰器，按拦截矩阵覆盖各方法、`subDirProvider` 持 `pathPrefix`） | 装饰器 + 测试（mock delegate） |
| 5 | `StorageProviderTools` 五个工具方法加 `catch (FileAclException)` | 工具类更新 + 测试更新 |
| 6 | `FileAclProperties`（`@ConfigurationProperties` + `toConfig()`）+ yml 样例 | 可选 yml 绑定 + 测试 |
| 7 | 集成测试：`StorageProviderTools` + 装饰器 + `LocalFileStorage`（`@TempDir`）端到端 | 集成测试用例 |
| 8 | 文档：更新 utils 模块 `AGENTS.md` / `CLAUDE.md`（如存在） | 文档同步 |

> **无 Spike 步骤**：与 mcp-server 方案不同，本方案不依赖切面触发与异常透传（最大不确定性），装饰器是普通 Java 包装、行为确定，无需可行性验证。

## 十、风险与已知限制

| 风险 / 限制 | 影响 | 应对 |
|---|---|---|
| **`listDirectory` / `glob` / `grep` 不做逐条结果过滤** | 被拒路径的**文件名**仍可能出现在列表中（内容读不到） | 本期仅判基路径可读性；逐条过滤作为增强项后续迭代（与 mcp-server 方案一致） |
| **拒绝抛异常会泄漏路径存在** | `exists(deniedPath)` 抛 `FileAclException` -> 智能体得知该路径存在且被拒 | 待确认事项 1：若需隐藏，改为 `exists`/`isDirectory` 对 DENY 路径返回 `false`（路径看似不存在），仅内容读/写抛异常 |
| **`subDirProvider` 路径还原** | 子装饰器看到的路径是 subDir 相对，需拼 `pathPrefix` 还原到根相对才能匹配 ACL | 装饰器持 `pathPrefix`，判定前拼接；测试覆盖 |
| **多工作区需多实例** | utils 一个 `StorageProvider` = 一个工作区 = 一份 ACL；多租户应用需为每租户构造独立装饰器 | 符合 SDK 模型；隔离由 base 存储根 / OSS 前缀保证 |
| **split-package 不惠及 mcp-server** | 本方案只覆盖 utils 消费者（用 `StorageProviderTools` 的应用）；mcp-server 有自己的 `StorageProvider` 与权限方案 | 设计如此；两份接口独立演进 |
| **`Edit` 在只读路径的失败阶段** | 胜出规则 `READ` 时，`Edit` 的 `readString` 放行、`writeString` 拒绝 -> 智能体读到内容却改不了 | 符合预期；错误串明确提示 write 被拒 |
| **配置错误（priority 冲突 / pattern 非法）** | 规则意外覆盖或 `AntPathMatcher` 抛异常 | `FileAclMatcher` 构造时预编译校验 pattern 合法性；测试覆盖典型冲突场景 |

## 十一、待确认事项

1. **拒绝语义：抛异常 vs 隐藏路径**。推荐**抛 `FileAclException` + `StorageProviderTools` 转友好串**（语义明确、实现简单、与 mcp-server 方案一致）。若评审更看重「不泄漏路径存在」，则对 `exists` / `isDirectory` / `getInfo` 的 DENY 路径返回中性值（`false` / `exists=false`），仅内容读写在 `readString` / `readAllLines` / `readImage` / `writeString` 等抛异常--代价是 `StorageProviderTools.read` 会先返回 `"File does not exist"`（因 `exists` 返回 false），语义变为「被拒路径看似不存在」。

2. **配置来源**。推荐**程序化注入为主、yml 为辅**（SDK 习惯，应用装配时构造 `FileAclConfig`）。是否需要同时提供 `FileAclProperties`（`@ConfigurationProperties`）以便 yml 驱动？utils 无 autoconfig，yml 路径需应用自行 `@EnableConfigurationProperties`。

3. **`default-policy` 默认值**。`allow-all`（未配置路径不受限，向后兼容）还是 `deny-all`（白名单式，未显式 allow 即禁）？推荐 `allow-all`，与 mcp-server 方案对齐。
