# 第一部分:一页纸速览(给完全没接触过的人先读这页)

## 这个项目一句话是什么
一个**"文件操作中间件"**:多个 AI 助手(Agent)不直接读写文件,而是统一通过这个服务来读写;这个服务负责保证每个用户/会话只能动自己那部分文件,且操作可追溯、可回滚。底层文件存在阿里云对象存储(OSS)上。

## 为什么需要它(大白话)
各家 AI 助手本来都自带"读写文件"的工具,但每个都得自己防"越权看别人文件""误删"等问题,重复造轮子还容易出漏洞。既然这些助手都支持同一个通信协议(MCP),那就:关掉它们自带的文件工具,全部改用这一个安全的服务--**安全规则只写一份,所有助手都受益**。

## 5 个必懂概念(看懂全文的前提)
| 概念 | 白话解释 |
|---|---|
| **MCP** | 一种"AI 助手调用外部工具"的标准协议。助手按这个协议发请求,服务按这个协议回结果。本服务就是一个 MCP 服务端。 |
| **Agent(智能体)** | 各种 AI 助手(项目里叫 openclaw/hermes/qwenpaw 等),是本服务的"客户"。 |
| **工作区(Workspace)** | 每个用户在存储里有一块独立"地盘",互不可见。这是隔离的基本单位。 |
| **OSS(对象存储)** | 阿里云的云存储,文件按"Key(路径名)"存放。本服务把所有文件都存这里。 |
| **快照(Snapshot)** | 改文件前自动存一份"旧版本",出问题能一键退回去。 |

# 第二部分:完整章节提纲(每章带导读,可照此撰写)

## 1. 背景与目标
> **导读**:让读者先明白"为什么要有这个东西"。读完应能回答:解决谁的什么痛点?目标和非目标各是什么?

- 1.1 **业务背景**:多个 AI 助手各自实现文件工具,安全能力重复建设、易出漏洞
- 1.2 **核心痛点**:未授权文件访问、误操作不可逆、按用户开沙箱成本高
- 1.3 **设计目标**:用一句话讲清"develop once, secure all agents"(安全规则写一次,所有助手都安全);文件能力与沙箱分离以降本
- 1.4 **非目标**:明确"不做什么"--不负责执行 shell/浏览器(那是沙箱的事),不替代云存储本身

## 2. 方案概述与定位
> **导读**:一句话定义它是什么,它在整个系统里处于什么位置。读完应能向同事用两句话介绍清楚。

- 2.1 **一句话定位**:基于 Spring AI 的 MCP 服务端,对外提供隔离的文件操作
- 2.2 **在整个系统中的位置**:助手 -> 本服务 -> 云存储;本服务是"安全网关 + 能力提供者"
- 2.3 **核心价值**:安全集中化、资源复用、协议标准化

## 3. 总体架构
> **导读**:这是全文最重要的一章。用一张图 + 顺着图讲"一次请求从进来到出去经过哪些环节",让读者建立全局画面。

> 📐 **配图:图1 总体架构(框图)**(`docs/architecture.drawio` 第1页)--分层容器框图:工具层列出 FileSystemTools 各工具(Read/Write/Edit/Glob/Grep/Trash/Rewind 等),中继含浏览器/办公/业务系统接口;下分工厂鉴权层、装饰器层、存储实现层(含快照)、配置层;外部实体(客户端、下游 MCP、OSS)无箭头连线;不绑定具体智能体。

- 3.1 **架构总览图**:助手 -> 鉴权 -> 工厂 -> 工具 -> (可选包装层) -> 内容处理 -> 云存储
- 3.2 **一次请求的完整旅程**(叙事化讲解,这是让外行懂的关键):
  > 📐 **配图:图2 工具代理逻辑**(`docs/architecture.drawio` 第2页)--所有工具通用的代理逻辑:身份识别 -> 装配隔离存储 -> 装饰器增强 -> 执行 -> 返回,不区分具体工具。

  1. 助手带着"我是谁"的身份标识发来请求
  2. 服务先验明身份,算出"你只能用这块地盘"
  3. 根据身份造一个"只看得见你这块地盘"的存储实例
  4. 调用对应工具(读/写/搜索…)
  5. 若开了配额/监控,在外层"套一层"再执行
  6. 真正读写云存储时,用流式方式处理内容(防内存爆掉)
- 3.3 **分层职责**:鉴权层 / 工具层 / 存储层 / 配置层 各管什么、边界在哪
- 3.4 **四条核心设计原则**(每条配白话解释):
  - 工具层不直接碰存储和鉴权(统一走"工厂"拿隔离实例)
  - 内容处理与存储解耦(解析逻辑只写一份,换存储不用改)
  - 用"装饰器"实现可插拔(像套包装,关掉就还原,零开销)
  - 所有路径都过一个安全函数(强制限制在自己目录内)

## 4. 工作区隔离模型
> **导读**:这是本服务的安全根基。读完应能回答:凭什么用户 A 看不到用户 B 的文件?

> 📐 **配图:图3 工作区隔离与安全细则(左半)**(`docs/architecture.drawio` 第3页)--身份(抽象)如何映射为独占的隔离前缀。

- 4.1 **身份怎么来**:从请求中携带的身份标识解析(当前实现为请求头格式,属测试期方案,可演进为独立鉴权模块)
- 4.2 **怎么变成隔离边界**:身份 -> 存储路径前缀 -> 每个用户/会话独占一块
- 4.3 **从助手视角看世界**:`pwd` 就是当前目录,所有路径都是相对的;**绝对路径直接拒绝**(防越权)
- 4.4 **多租户语义**:不同身份之间数据彻底隔离

## 5. 核心能力总览(对外提供什么)

- 5.2 **查找类**:按文件名模式搜索(Glob)、按内容正则搜索(Grep)
- 5.3 **目录与回收站**:列目录、软删除(进回收站可恢复)
- 5.4 **版本安全类**:查历史快照、一键回滚
- 5.5 **文件分享**:生成临时下载链接给用户
- 5.6 **Skill 能力**:列出/读取工作区内的"技能说明文档"
- 5.7 **(可选)工具中继**:代理下游的浏览器/命令行等工具

## 6. 核心模块详细设计
> **导读**:这是技术方案的"主体"。每个模块按"它管什么 -> 关键流程 -> 为什么这么设计"展开。读者读完后应能理解每个内部组件存在的理由。

### 6.1 MCP 工具层(对外门面)
> 📐 **配图:图4 文件系统交互流程**(`docs/architecture.drawio` 第4页)--工具与文件系统的交互:读取 / 修改 / 删除三类操作的不同处理路径与安全前置。

- **管什么**:把文件能力包装成 MCP 工具,供助手调用
- **关键点**:每个工具第一步都是"按当前请求拿一个隔离的存储实例",自身不碰鉴权和存储细节
- **多媒体读取怎么分流**:按文件扩展名决定走文本/图片/PDF/Office 哪条解析路径
- **为什么这么设计**:工具层保持"薄",只做参数校验和分发,安全和存储逻辑集中可维护

### 6.2 Skill 工具与资源
- **管什么**:让助手能发现并读取工作区里的"技能说明"
- **两种访问形态**:工具(主动调用)与资源(按 URI 拉取),适配不同助手 SDK 的习惯
- **为什么这么设计**:双通道提升兼容性

### 6.3 存储抽象层(隔离的核心)
- **管什么**:定义文件操作契约,按身份造隔离实例,封装云存储细节
- **关键流程**:身份 -> 拼路径前缀 -> 造一个"只看得见自己目录"的存储实例
- **安全核心**:所有路径都过一个统一函数--空路径返回根、绝对路径报错、其余拼接进前缀内
- **为什么这么设计**:换存储后端(如 S3/本地盘)时,只需新写一个实现,上层全部复用

### 6.4 内容处理层(防 OOM 的关键)
- **管什么**:所有文件解码/格式化的唯一落点
- **关键点**:只接受"流"(InputStream),逐块处理,不一次性把大文件读进内存
- **为什么这么设计**:防大文件撑爆内存;且解析逻辑与存储解耦,换存储零改动

### 6.5 快照与回滚
> 📐 **配图:图6 文件与执行安全多重保障(机制②)**(`docs/architecture.drawio` 第6页)--版本快照与回退:写/编辑前自动快照,支持 Rewind 回退。

- **管什么**:改文件前自动存旧版本,支持回退
- **关键流程**:写/编辑/软删前自动存一份 -> 元数据记录"改的哪个文件、什么动作、什么时间" -> 回滚时先存"当前状态"再恢复旧版本(撤销也能再撤销)
- **为什么这么设计**:防止助手误操作或危险脚本造成不可逆破坏;回滚前的二次快照保证"回滚本身也能后悔"
- **隐藏性**:快照目录对普通列目录不可见,不污染用户视野

### 6.6 存储配额
> 📐 **配图:图5 配额装饰器流程**(`docs/architecture.drawio` 第5页)--writeString 的拦截/校验/计费逻辑,展示装饰器如何"套"在真实存储外。

- **管什么**:限制每个工作区最多用多少存储,防滥用
- **关键流程**:用一个元文件记"已用多少";每次写入算增量差额并校验是否超限;定期(默认 24 小时)全量重算纠偏
- **装饰器实现**:在真实存储外"套一层",只拦截会改变占用的操作(写/删/移动),读取类直接放行
- **为什么这么设计**:增量计费省成本,定期全量保证准确;用装饰器让配额可一键开关、关掉零开销

### 6.7 工具中继与懒加载沙箱

> 📐 **配图:图6(执行沙箱侧)**(`docs/architecture.drawio` 第6页)--MCP Server 通过 RelayTools + LazyLoadSandboxCreator 中继到下游沙箱 MCP Server;沙箱隔离是下游职责,非本服务自身机制。

- **管什么**:把下游 MCP Server 的工具"转手"给助手用。下游包括:沙箱 MCP Server(shell/python/browser)、办公系统 MCP Server、业务系统 MCP Server。
- **中继实现**:`RelayTools`(~40 个 `@McpTool`,含 `browser_*`/`run_shell_command`/`run_ipython_cell` 等)通过 `RelayMcpClientManager` 每请求创建一个到下游 MCP Server 的连接并经 `RelayMcpClientManager` 初始化,使用后关闭。
- **懒加载沙箱机制**:
  - `LazyLoadSandboxCreator`:预读取下游沙箱 MCP Server 的工具列表,按 **ALLOWED_TOOL_NAMES 白名单**过滤(允许 `run_shell_command`、`run_ipython_cell`、全部 `browser_*` 共 25 个工具,拒绝名单外工具)
  - `LazyLoadSandboxToolsService`:提供**懒加载**工具回调--仅在 Agent 实际调用沙箱工具时才真正创建 McpSyncClient 连接沙箱,避免 Agent 未使用沙箱时也预创建沙箱 Pod 造成资源浪费;使用后需 `closeMcpClient()` 防止堆外内存泄漏
- **身份透传**:通过 `x-agentrun-session-id` 请求头把 agentId 传给下游,下游 MCP Server 据此创建或连接独占沙箱
- **传输协议支持**:支持 `streamable-http` 和 `sse` 两种下游 MCP 传输
- **为什么这么设计**:沙箱隔离由下游独立 MCP Server 负责(容器级隔离、工作区挂载);本服务只做中继和懒加载控制,职责分离;资源浪费是核心问题,懒加载模式解决了"Agent 不用沙箱也占用 Pod"的问题

### 6.8 管理 REST 接口
- **管什么**:供前端/运维直接管理文件和工作区(独立于 MCP 协议)
- **两套接口**:用户工作区接口(凭身份头)+ 管理员接口(凭管理员令牌,可跨工作区操作)
- **为什么这么设计**:运维和用户自服务场景需要 HTTP 直连,不走 MCP 协议

## 7. 安全设计
> **导读**:这是项目的核心卖点,单独成章重点写。读完应让评审相信"隔离是可靠的、信息不会泄露"。

> 📐 **配图:图6 文件与执行安全多重保障**(`docs/architecture.drawio` 第6页)--文件系统侧(隔离/快照/回收站,本服务保障)+ 执行沙箱侧(python/shell/browser_use,由下游 sandbox-mcp MCP Server 通过懒加载中继提供,本服务不自持沙箱容器)。

- 7.1 **身份与鉴权**:身份从哪来、怎么校验、格式错误怎么拒
- 7.2 **路径安全**:绝对路径拒绝、`..` 跨目录的处理、云存储路径语义说明

> 📐 **配图:图3 安全细则(右半)**(`docs/architecture.drawio` 第3页)--五条安全原则:路径约束、绝对路径拒绝、内部目录隐藏、信息脱敏、身份唯一来源。

- 7.3 **数据隔离**:工作区前缀硬隔离;内部目录(快照/回收站/影子缓存)对用户隐藏
- 7.4 **信息脱敏**:报错和返回里不含存储真实路径,只给相对路径
- 7.5 **管理员通道**:独立令牌鉴权,与用户通道分离
- 7.6 **执行沙箱隔离**:本服务不自持沙箱容器。执行类操作(python/shell/browser)通过 `LazyLoadSandboxCreator` + `RelayTools` 中继到下游独立的 `sandbox-mcp` MCP Server;沙箱的容器级隔离、工作区挂载、资源限制均由下游 MCP Server 负责。本服务通过白名单(`ALLOWED_TOOL_NAMES`,25 个工具)和懒加载(Agent 实际调用时才创建连接)做前置控制。
- 7.7 **已知待办与加固路线**:诚实列出还没做完的安全项(鉴权模块独立化、路径归一化)
